### Integration and realtime

- HIS Adapter pattern

- SSE or WebSocket for live journey/location updates
- QR baseline location provider
- Zigbee integration through MQTT/Zigbee2MQTT and a positioning service when enabled

### Deployment

- Docker Compose for local/hackathon
- Kubernetes-ready boundaries for later production deployment

## Backend modules

This section is the canonical description of the `apps/api` internal structure. Rationale lives in [ADR-0007](../adr/0007-hexagonal-modules-transaction-in-context.md) (hexagonal modules, transaction-in-context) and [ADR-0001](../adr/0001-monorepo-modular-monolith.md) (modular monolith); other documents reference this section instead of duplicating it.

Planned module list — a module gets a package when it has real features, never as an empty skeleton:

```text
identity       (implemented, incl. identity/line verifier)
visit          (implemented — deprecated per ADR-0009, superseded by journey)
journey        (implemented — CarePath-owned journey plan derived from HIS facts, ADR-0008 amended by ADR-0009)
servicepoint   (implemented)
hospitalmap    (implemented, #24)
navigation     (planned)
location       (planned)
notification   (planned)
integration    (implemented as internal/his, incl. the his/ingest event-feed poller)
```

Current `apps/api` layout:

```text
apps/api/
├── cmd/server/main.go      # composition root — wiring only
├── docs/                   # generated by swaggo (make swag); committed, never edited
└── internal/
    ├── platform/db/        # pgxpool + Transactor + Querier (shared infrastructure)
    ├── his/                # integration module: Client port (snapshot + event feed)
    │   ├── httpclient/     # HTTP adapter for packages/contracts/openapi/mock-his.yaml
    │   └── ingest/         # event-feed poller driving the journey projection
    │       └── postgres/   # durable feed cursor (checkpoint)
    ├── servicepoint/       # domain type + Repo port + Service
    │   └── postgres/       # pgx adapter implementing the Repo port
    ├── visit/              # domain types + Service + HTTP handler (live HIS read view)
    └── journey/            # journey projection (derived state, eventId-idempotent apply)
        └── postgres/       # pgx adapter implementing the Repo port
```

Internal shape per module — flat layer files in one package, subpackages only for adapters:

```text
module/
├── <name>.go    # domain types + the module's Repo port
├── service.go   # Service interface (the only cross-module entry point) + business logic
├── handler.go   # HTTP handlers (omit for modules without routes)
└── postgres/    # pgx adapter implementing Repo
```

Rules (full detail in ADR-0007): dependencies point inward (handler → service → Repo port ← postgres adapter); services own transaction boundaries via `db.Transactor` and share them through ctx; cross-module calls go through the callee's Service only, never its Repo. Ports/adapters can be adopted progressively without forcing microservices.

Error model: modules expose domain error variables built with `apperr.New(kind, message)` (`internal/platform/apperr`); kinds map to statuses 400 invalid, 401 unauthorized, 403 forbidden, 404 not found, 409 conflict, 500 internal, 502 upstream. Only `httpx.Error` (the HTTP boundary) performs the mapping and logging — internal (500) causes are masked to a generic client message while the detail stays in the request log.

## Navigation approach

SVG is presentation; routing uses a graph.

- `NavNode`: floor, x, y, type
- `NavEdge`: from, to, distance, accessible, direction
- Algorithm: Dijkstra first; A* is a compatible future optimization

## Floor-plan approach

Floor-plan SVG elements should carry stable IDs/data attributes, for example:

```xml
<rect id="room-blood-collection" data-place-id="LAB-01" />
<rect id="room-pharmacy" data-place-id="PHARMACY-01" />
```

The plans live in `packages/floorplans/` — `floors/*.svg` for the visual layer and `graphs/*.json`
for the matching `NavNode`/`NavEdge` data. See that package's README for the full element/attribute
convention (`room-*`, `node-*`, `data-place-id`, `data-zone`, `route-layer`).

The frontend overlays current position, destination, and the computed route without embedding business flow into the SVG itself.
